공장 건설의 전체 흐름 (EPC)

화학 공장, 정유 공장, 가스 처리 시설… 이런 곳을 짓는 일을 EPC(Engineering, Procurement, Construction)라고 해요. 간단히 말하면: 설계(E) → 자재 구매(P) → 시공(C) 순서예요.

PKU(필즈엔지니어링)는 이 EPC 과정에서 "도면 검토" 단계에 AI를 쓰고 싶어합니다. 수백 장의 도면을 사람이 일일이 검토하는데, 이걸 AI가 먼저 훑어서 실수를 잡아주길 원하는 거예요.

Chapter 2 · IFC
IFC가 뭐야? — 도장 찍기 전 마지막 관문
Issued For Construction. 공사 시작 허가를 받은 도면입니다.
🏫 초등학생 비유

학교 시험지가 있다고 생각해봐요.
선생님이 시험지를 학생들한테 주기 전에 "오타 없는지, 문제 빠진 건 없는지" 검토하죠?
IFC 도면은 바로 그 "학생들한테 나눠주기 전 최종 시험지"예요.
공사 현장 인부들이 이 도면을 보고 실제로 파이프를 잇고 장비를 세우기 때문에, 여기서 실수가 나오면 수십억 원짜리 재작업(LD)이 발생해요.

IFC 도면이란?

설계가 충분히 완성되어서 실제 공사에 사용할 수 있는 상태의 도면이에요. 이 단계 이전에는 "검토용(IFR)", "승인용(IFA)" 등 여러 단계가 있어요.

IFC 이전에 AI가 검토한다 = 사람 엔지니어가 PE(전문엔지니어) 도장 찍기 전에, AI가 먼저 훑어서 실수를 잡아준다는 뜻이에요.

❌ IFC에서 실수가 나오면?
  • 🔧 현장에서 이미 설치한 파이프를 다시 뜯어내야 함
  • 💰 재작업(Rework) 비용 — 공사비의 평균 9%
  • ⏰ 공기 지연 → LD(지연배상금) 폭탄
  • 😰 $500M 프로젝트면 LD 5% = $25M
✅ AI가 검토해주면?
  • 🤖 수백 장 도면을 몇 분 안에 훑어봄
  • 🔍 놓치기 쉬운 분야 간 충돌 감지
  • 📋 검토 결과 보고서 자동 생성
  • 👨‍🔧 사람 엔지니어는 AI가 찾은 것만 집중 확인

집을 지을 때 목수, 전기기사, 배관공, 인테리어 디자이너가 따로 있죠?
공장도 마찬가지예요. 8개 전문 팀이 각자 자기 도면을 만들어요.

Chapter 4 · General Checklist A~F
모든 분야에 공통으로 적용되는 6가지 검토 항목
8개 팀 모두에게 묻는 공통 질문입니다. AI가 가장 먼저 처리할 영역이에요.
A
Document Control & Revision Integrity — "서류가 제대로 돼 있나?"
🏫 초등학생 비유

시험지에 이름·날짜·반 번호가 제대로 적혀있는지 확인하는 것과 같아요. 이름이 틀리면 채점도 못 하잖아요.

AI가 확인할 항목들
프로젝트 이름·번호·클라이언트명 일치 여부 / 도면 제목·분야 코드 정확성 / IFC 리비전 표시 / 리비전 히스토리 완전성 / 도면 번호 중복 여부 / 크로스 레퍼런스(다른 도면 참조) 일관성 / 도면 인덱스와 실제 패키지 일치
// AI Rule 예시 — A 섹션 { "rule_id": "A-001", "check": "project_number_match", "description": "도면 표제란의 프로젝트 번호가 패키지 인덱스와 일치하는지", "source": "title_block.project_no", "target": "package_index.project_no", "result": "PASS | WARNING | FAIL" }
개발 포인트: PDF 도면의 표제란(Title Block)에서 텍스트를 추출해 DB와 비교하는 기능이 필요해요. OCR + 정규표현식으로 처리할 수 있는 가장 기본적인 영역입니다.
B
Engineering Completeness — "내용이 다 있나? 빠진 건 없나?"
🏫 초등학생 비유

요리 레시피에 재료는 있는데 조리 순서가 빠져있다면? 요리를 만들 수 없잖아요. 도면도 마찬가지예요. 치수·높이·재질 중 하나라도 빠지면 공사를 못 해요.

AI가 확인할 항목들
단면·상세 뷰·콜아웃 누락 여부 / 치수 완결성 / 높이(Elevation) 표시 / 재질·사양 명시 여부 / 공차(Tolerance) 기재 / 가설조건과 실제 설계 일치 / 시공 노트 완성도
개발 포인트: "빠진 것을 찾는" 작업이라 단순 텍스트 검색보다 어렵습니다. 필수 요소 체크리스트(required elements list)를 도면 유형별로 미리 정의하고, 있어야 할 게 없으면 FAIL을 반환하는 방식으로 접근해요.
C
Interdisciplinary Physical Coordination — "팀끼리 충돌하지 않나?"
🏫 초등학생 비유

방 꾸미기를 여러 명이 나눠서 할 때 — 한 명은 거기에 책상 놓겠다 하고, 다른 명은 거기에 소파 놓겠다 하면 둘 다 들어갈 수 없잖아요. 공장에선 이게 수십억 짜리 실수예요.

AI가 확인할 항목들 (가장 중요한 영역!)
배관 경로 vs 케이블 트레이 충돌 / 장비 위치 vs 구조 기둥 충돌 / 배관 관통부 vs 구조 부재 위치 / 유지보수 공간 확보 여부 / 지하 배관 vs 지하 구조물 충돌 / 계장 접근성 확인
개발 포인트: 이건 2D 도면만으로는 한계가 있어요. 이상적으로는 3D 모델 데이터(좌표 정보)를 파싱해서 충돌을 감지해야 합니다. 초기에는 "같은 좌표에 서로 다른 분야 요소가 표시돼 있는가"를 체크하는 방식으로 시작할 수 있어요.

실제 EPC에서 분야 간 충돌이 어떻게 발생하고 어떻게 해결하는지 사례 중심으로 설명합니다.

D
Constructability Review — "실제로 지을 수 있나?"
🏫 초등학생 비유

레고 설명서가 아무리 완벽해도, 손이 너무 커서 작은 칸에 레고를 끼울 수 없으면 소용없잖아요. 도면이 완벽해도 현장에서 실제로 못 지으면 의미 없어요.

AI가 확인할 항목들
크레인 접근 가능성 / 조립 순서 타당성 / 용접 접근성(볼트 조이는 공간) / 수송 제한 검토 / 모듈화 인터페이스 / 가설 지지대 요구사항 / 현장 조립 공차
개발 포인트: AI가 "현장에서 가능한가"를 판단하려면 시공 제약 조건 DB가 필요해요. 예: "볼트 간격 최소 X mm 이상", "크레인 접근 반경 Y m 이상". 이 조건들을 엔지니어와 함께 수치화하는 작업이 선행돼야 합니다.
E
Safety & Operability — "사람이 안전하게 일할 수 있나?"
🏫 초등학생 비유

학교 비상구가 막혀있으면 안 되죠? 공장은 불이 나거나 가스가 새면 사람이 빠져나갈 수 있어야 해요. AI가 이 안전 항목들을 먼저 체크해줍니다.

AI가 확인할 항목들 (가장 중요한 영역 2!)
비상구·탈출로 확보 여부 / 방폭 구역 분류 적용 / 방화·방폭 처리 / 유지보수 접근성 / 드레인·벤트 안전 처리 / 인체공학적 조작성 / 밀폐공간 식별
개발 포인트 (최우선): 안전 항목은 AI가 틀리면 실제 인명 피해로 이어질 수 있어요. False Negative(실제 문제를 AI가 놓치는 것)를 최소화하는 게 False Positive보다 훨씬 중요합니다. "의심스러우면 WARNING"이 기본 원칙.
📚
CELab Wiki — PSV/HAZOP 안전 시스템 (Vijay Sarathy, 강의 09)
안전 시스템 설계의 핵심 — PSV(압력 안전 밸브) API 520 기준, HIPPS(고압 차단 시스템), SIL(안전 무결성 등급)을 엔지니어링 관점에서 설명합니다.
Module 15~17 안전 시스템 IEC 61511 SIL 표준 PSV 자동 검토 시나리오
F
IFC Readiness Verification — "이제 공사 시작해도 될까?"
🏫 초등학생 비유

시험지 제출 전 최종 점검표예요. "이름 썼나? 빈칸 없나? 계산기 챙겼나?" 도면도 IFC로 나가기 전에 이 목록을 다 통과해야 해요.

AI가 확인할 항목들
설계 충분히 완성됐는가 / 미해결 코멘트 있는가 / 벤더 데이터 반영됐는가 / 설계 가정이 문서화됐는가 / 필요한 계산서 완료됐는가 / Hold Point(보류 항목) 식별됐는가 / 현장 검증 필요 항목 표시됐는가
개발 포인트: "Open Comments(미해결 코멘트)"를 AI가 찾는 게 핵심이에요. 도면 내 코멘트 레이어, 리비전 클라우드(빨간 구름 표시), TBC/TBD 텍스트를 감지하는 파서가 필요합니다.
Chapter 5 · Rule Engine
AI가 배워야 하는 규칙 — Rule Engine 개념 설명
체크리스트 항목을 어떻게 기계가 이해할 수 있는 규칙으로 만드는가.
🏫 초등학생 비유

엄마가 "방 청소 해" 라고만 하면 어떻게 해야 할지 막막하죠?
"1. 바닥에 있는 것 다 줍기 2. 먼지 털기 3. 바닥 닦기 4. 쓰레기 버리기" 라고 구체적으로 써주면 할 수 있어요.
체크리스트 항목도 마찬가지예요. "P&ID와 레이아웃이 일치해야 한다"를 AI에게 가르치려면 구체적인 규칙으로 분해해야 해요.

Rule 템플릿 구조 (4단)
// 모든 Rule은 이 4가지 요소로 구성 { "rule_id": "PROC-001", // 고유 식별자 "condition": "P&ID의 Tag 번호가 존재할 때", // 언제 적용하나 "target": "Layout 도면에서 같은 Tag 검색", // 무엇을 확인하나 "criterion": "Tag가 Layout에도 있어야 함", // 기준은 무엇인가 "result": "없으면 FAIL / 있으면 PASS" // 결과 판정 }
Rule 난이도 3단계
L1
텍스트 비교 (쉬움) 자동화 즉시 가능
두 문서에서 같은 텍스트(Tag 번호, 프로젝트 번호)가 일치하는지 비교. 예: "P&ID의 Tag 번호 = Line List의 Tag 번호"
L2
수치 계산 (중간) 엔지니어 공식 필요
수치가 기준 범위 안에 있는지 확인. 예: "PSV 크기 ≥ 필요 오리피스 면적", "파이프 두께 ≥ 설계 압력 기준 최소값"
L3
맥락 판단 (어려움) AI + 전문가 협력 필요
"설계 의도가 맞는가"를 판단. 예: "이 제어 로직이 운전 시나리오와 일관성 있는가". 단순 규칙으로는 부족하고 LLM + 도메인 지식이 필요해요.

Chapter 6 · Codes & Standards
코드와 표준 — AI가 알아야 하는 "법"
엔지니어들이 따라야 하는 규격집. AI Rule을 만들 때 이 기준들이 근거가 됩니다.
🏫 초등학생 비유

도로에 신호등 규칙이 있잖아요. 빨간불엔 멈추고, 초록불엔 가고. 이 규칙은 나라마다 조금씩 달라요.
공장 설계도 마찬가지예요. "이 파이프 두께는 최소 X mm 이상이어야 한다"는 규칙이 있고, 그 규칙은 ASME(미국)인지 EN(유럽)인지에 따라 숫자가 달라요.
AI는 어느 프로젝트가 어느 나라 기준을 따르는지 알고 있어야 해요.

코드/표준 분야 무엇을 정하는가 PKU 체크리스트 연관
ASME B31.3 Piping 공정 배관 설계 기준 (두께, 재질, 용접) Piping Module 전체
API 520/521 Safety 압력 안전 밸브(PSV) 크기 계산 기준 E섹션 + Process Module
IEC 61511 I&C 안전 계장 시스템(SIS) SIL 등급 기준 I&C Module 안전 항목
NEC (NFPA 70) Electrical 전기 배선, 방폭 구역, 케이블 기준 Electrical Module 전체
API 610 Mechanical 원심 펌프 설계·성능 기준 Mechanical Module (펌프)
ACI / AISC Civil/Structural 콘크리트(ACI)·철골(AISC) 설계 기준 Civil + Structural Module
개발 중요 포인트: AI Rule은 "어느 코드 기준인지"를 파라미터로 받아야 해요. 같은 파이프 두께 계산이라도 ASME B31.3 vs EN 13480 결과가 달라요. 프로젝트 설정에서 applicable_codes[]를 등록하고 Rule Engine이 이를 참조하도록 설계하세요.

무엇부터 만들어야 하나? — 우선순위 가이드
W1
Week 1~2: 체크리스트 JSON 변환
PKU DOCX의 370개 항목을 위 구조로 변환. 분야·카테고리·난이도 태깅. Python + docx2python으로 시작.
W2
Week 2~3: PDF 파서 프로토타입
샘플 IFC 도면(PDF)에서 표제란 텍스트 + 태그 번호 추출. pdfplumber 또는 PyMuPDF로 시작. 일단 텍스트 추출만 돼도 50개 이상의 Rule을 적용 가능.
W3
Week 3~4: Section A Rule Engine
Document Control(A 섹션) 13개 항목부터 Rule 구현. 가장 단순한 텍스트 비교로 빠른 성과 가능. PKU에 시연할 MVP 후보.
W4
Week 5~6: Process + P&ID 모듈
Process Engineering 26개 항목 + Cross-discipline Tag 일관성 체크. P&ID 도면에서 태그 번호 파싱 + Line List CSV 비교가 핵심.
추천 기술 스택 (시작용)
  • PDF 파싱 pdfplumber, PyMuPDF
  • OCR Tesseract, Azure Document Intelligence
  • Rule DB SQLite → PostgreSQL (확장 시)
  • LLM (L3 판단) Claude API (claude-haiku-4-5)
  • API FastAPI (Python)
  • 프론트엔드 React + Tailwind
절대 하면 안 되는 것들
  • ❌ AI가 PASS 판정을 내리면 사람 검토 생략
  • ❌ 안전 항목(E섹션)에서 False Negative 무시

  • ❌ 엔지니어 없이 Rule 독자 개발 (전문가 필수)

Chapter 8 · Full Picture
전체 그림 — 3줄 요약
이 모든 걸 처음 보는 팀원에게 설명한다면.
개발자에게 전달할 3줄 요약
1. 우리가 만드는 건: 공장 건설 도면(IFC)이 공사 시작 전에 제대로 됐는지 검토하는 AI 어시스턴트. 수백 장의 도면을 8개 분야 전문가 입장에서 자동으로 훑고, 실수 가능성이 있는 곳을 엔지니어에게 알려줌.
2. 핵심 기술: PDF/CAD 파싱 → 텍스트·태그·수치 추출 → 약 370개 체크리스트 기반 Rule 적용 → 이슈 보고서 생성. Rule은 3단계(텍스트비교/수치계산/맥락판단)로 난이도가 다르고, 높은 단계일수록 LLM + 도메인 전문가 협력이 필요.
3. 개발 시작점: Section A(문서 제어) 13개 항목으로 MVP 먼저. PDF 파서 + 텍스트 비교 Rule만으로 빠른 시연 가능. 안전 항목(E섹션)은 False Negative 최소화가 최우선 원칙. AI는 보조, 최종 판단은 항상 사람 엔지니어.
