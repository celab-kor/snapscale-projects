공식 문서명
"AI-Assisted IFC Drawing QA/QC Review Checklist"
원래 용도: AI 기반 엔지니어링 QA/QC 리뷰 툴 개발의 기능 참조서(Functional Reference) + 리뷰 로직 가이드라인.
발행 목적: IFC(Issued For Construction) 도면과 관련 성과품에 대한 AI 리뷰 엔진 개발을 지원하기 위해 준비됨.
핵심 원칙 (PKU 원문): "The AI system should not merely perform keyword or drafting checks, but should emulate the review mindset of experienced multidisciplinary EPC engineering reviewers."

→ SnapScale이 만드는 것은 단순 키워드/서식 검사기가 아니라, 숙련 EPC 엔지니어의 검토 사고방식을 재현하는 AI입니다.
✅ AI가 해야 할 것
  • 🔍 잠재적 엔지니어링 불일치 식별
  • 🔗 분야 간 협조(Interdisciplinary Coordination) 이슈 감지
  • 🏗️ 시공성(Constructability) 및 운전성(Operability) 우려 사항 강조
  • 📄 문서 완결성(Documentation Completeness) 검토
  • ⚙️ IFC 릴리즈 및 PE 스탬프 전 엔지니어 지원
❌ AI가 대체하지 않는 것
  • 📜 프로젝트별 코드 및 표준 (별도 제공)
  • 👤 클라이언트 사양서
  • 📑 엔지니어링 절차서
  • 🧠 전문 엔지니어의 판단 (PE Judgment)
  • ⚖️ PE 법적 책임 (Responsible Charge)
Section 1 · MECE Analysis
CELab Wiki 온톨로지 × PKU 체크리스트

누락 없이, 중복 없이 — PKU 8개 분야를 CELab 4축 필터(EPC Stage · Domain · Question Type · AutoFlow)에 매핑합니다.

MECE 기준 설계: CELab Wiki의 인화공 Q&A 온톨로지(EPC Stage × Domain × Question Type × Product Link)를 PKU 체크리스트의 8 Discipline × 6 General Category에 교차 매핑. 신규 발견: Civil, Electrical, Architectural 3개 도메인이 CELab 현행 온톨로지에 미등록 → Ontology Gap 식별됨.

Section 2 · Jobs To Be Done Framework
JTBD — 5 Core Jobs

SnapScale가 PKU 체크리스트를 받았을 때 "수행해야 할 핵심 업무"를 JTBD 형식으로 정의합니다.
JTBD 구조: 상황(When) + 동기(We need to) + 기대 결과(So that)

Job 1 · Parse & Classify
클라이언트의 엔지니어링 QA 요구사항을 AI가 처리 가능한 구조로 변환
When: 클라이언트로부터 엔지니어링 체크리스트 문서(DOCX/PDF/Excel)를 수령했을 때
We need to: 모든 체크 항목을 분야·단계·유형별로 MECE하게 분류하고 기계 판독 가능한 형식으로 구조화
So that: AI 엔진이 각 항목에 대해 실제 도면을 검토하는 로직을 적용할 수 있도록
Functional Jobs
  • DOCX → 구조화된 JSON/DB 변환
  • 8 Discipline 분류 자동화
  • CELab 온톨로지 매핑
  • 중복/모순 항목 감지
  • Gap 분석 보고서 생성
Social Jobs
  • 클라이언트에게 "우리는 체계적"임을 증명
  • EPC 전문성 보유 증명
  • 내부 팀 온보딩 속도 향상
Emotional Jobs
  • 팀이 "놓친 게 없다"는 확신 확보
  • 범위 명확화로 불안 해소
  • 반복 가능한 방법론 확립 만족
담당: SnapScale AI팀 산출물: Structured Checklist DB 기간: Week 1~2
Job 2 · Rule Extraction
자연어 체크리스트를 AI 리뷰 로직(Rules)으로 변환
When: 구조화된 체크 항목이 준비되었을 때
We need to: 각 항목을 "어떤 도면에서, 무엇을, 어떻게 확인하는가"의 검증 가능한 규칙으로 변환
So that: AI가 실제 IFC 도면 파일에 적용할 수 있는 실행 가능한 검토 로직이 완성되도록
Functional Jobs
  • Rule template 설계 (조건-대상-기준)
  • 분야별 Rule set 작성
  • 우선순위 Rule 선별 (Pareto: 20% → 80%)
  • 예외 조건 식별
  • Rule 버전 관리 체계
Social Jobs
  • PE 급 검토자와의 신뢰 구축
  • 엔지니어 언어로 소통 가능한 AI 증명
  • PKU 내부 검토 통과
Emotional Jobs
  • "AI가 실제로 이해한다"는 신뢰
  • 규칙 기반 투명성으로 블랙박스 우려 해소
  • 엔지니어 참여 의지 증가
담당: SnapScale + PKU 검토팀 산출물: Rule Engine v0.1 기간: Week 3~6
Job 3 · Document Parsing
IFC 도면/문서 파일에서 AI 검토 가능한 데이터 추출
When: AI가 실제 IFC 도면(PDF, P&ID, GA, 배관 레이아웃 등)을 입력받았을 때
We need to: 텍스트·태그·치수·기호를 구조화된 데이터로 파싱하여 Rule Engine에 공급
So that: 각 체크 항목의 충족 여부를 자동으로 판단할 수 있도록
Functional Jobs
  • PDF/CAD 텍스트 추출
  • Tag 번호·좌표 파싱
  • 도면 메타데이터 추출 (Rev, Title, Sheet)
  • 멀티-도면 상호 참조
  • 데이터 일관성 교차 검증
Social Jobs
  • 기존 EPC 워크플로와의 호환성 증명
  • CAD/DCC 통합 가능성 시연
Emotional Jobs
  • 실무 파일 바로 처리 가능한 툴이라는 확신
  • 특별 변환 작업 없이 사용 가능
담당: SnapScale 개발팀 산출물: Document Parsing Engine v0.1 기간: Week 3~8
Job 4 · Review Execution & Reporting
AI 리뷰 결과를 엔지니어가 신뢰하고 활용할 수 있는 보고서로 전달
When: Rule Engine + Document Parser가 결과를 생성했을 때
We need to: 체크 항목별 통과/주의/실패 결과를 근거와 함께 표시하고, PE 최종 판단을 지원하는 형식으로 보고
So that: 엔지니어가 AI 리뷰 결과를 검토하고 IFC 릴리즈 여부를 결정할 수 있도록
Functional Jobs
  • 리뷰 대시보드 설계
  • 이슈 우선순위 자동 분류
  • 근거 문서 참조 연결
  • 리뷰 이력 추적
  • PDF 보고서 내보내기
Social Jobs
  • PE 스탬프 전 공식 QA 기록 제공
  • 감사(Audit) 이력 확보
  • 클라이언트와 공동 검토 가능성
Emotional Jobs
  • 리뷰어가 "AI가 도와준다"는 파트너 감각
  • 놓친 항목에 대한 두려움 감소
  • LD 리스크 감소 확신
담당: SnapScale UX + PM 산출물: Review Dashboard v0.1 기간: Week 9~12
Job 5 · Methodology Scaling
PKU에서 검증한 방법론을 다른 클라이언트에게 반복 적용할 수 있는 표준화된 프로세스로 전환
When: PKU POC가 완료되고 결과가 나왔을 때
We need to: 체크리스트 → MECE → 태스크 → AI 개발 → 보고의 전체 파이프라인을 표준 템플릿화
So that: 새 클라이언트로부터 체크리스트를 받을 때마다 2배 빠르게 시작하고, 내부 학습 비용을 최소화하도록
Functional Jobs
  • 프로젝트 갤러리 구조 설계
  • 방법론 문서화 (이 문서)
  • 체크리스트 분류 자동화 스크립트
  • Rule 재사용 라이브러리 구축
  • KPI 벤치마크 데이터 누적
Social Jobs
  • SnapScale = "EPC AI 방법론 표준" 포지셔닝
  • 다음 클라이언트 영업 레퍼런스
  • 팀 역량 외부 가시화
Emotional Jobs
  • 팀이 "우리만의 방법론이 있다"는 자부심
  • 반복 가능성에서 오는 심리적 안정감
  • 성장 가시화
담당: 김상윤 대표 + 전략팀 산출물: SnapScale Project Playbook v1 기간: Week 17~20
Section 3 · Execution Plan
PKU POC 실행 계획 — 마일스톤 & 태스크

JTBD 5개 Job을 4개 Phase로 분해하고 태스크·담당자·기간을 배정합니다. 총 예상 기간: 20주 (5개월)

실행 원칙: (1) Process + Piping + I&C 먼저 — O&G EPC의 핵심 가치 창출 영역. (2) 도메인 전문가와 동시 작업 — AI 규칙 개발은 엔지니어 검토 없이 단독 불가. (3) 각 Phase 완료 시 PKU와 중간 리뷰 — 방향 조정 기회 확보.
Phase 1 · Foundation — 체크리스트 구조화 + 인프라 구축
Week 1~4
KPI: 전체 ~370개 항목 100% 구조화 완료 | CELab 온톨로지 매핑 완료 | Gap 3개 분야 분류 체계 확정
T1.1 전체 체크리스트 JSON 변환 (8 Discipline × 항목별 구조화) AI팀
T1.2 CELab 온톨로지 매핑 + Gap 분석 문서 작성 PM + AI팀
T1.3 IFC 도면 파싱 파이프라인 프로토타입 (PDF→텍스트+태그 추출) 개발팀
T1.4 테스트 데이터셋 준비 (PKU 제공 샘플 IFC 도면 3~5종) PM → PKU 협의
T1.5 Rule 템플릿 설계 (조건-대상-기준-결과 4단 구조) AI팀 + 엔지니어
Phase 2 · Core Engine — Process / Piping / I&C 모듈 개발
Week 5~10
KPI: 3개 핵심 분야 Rule coverage ≥60% | 샘플 도면 리뷰 정확도 ≥70% (PE 판단 대비) | False Positive ≤30%
T2.1 Process Engineering Module — P&ID 일관성, PSV 크기, Relief 시나리오 Rule 개발 AI팀 + Process Eng.
T2.2 Piping Engineering Module — Pipe class/spec, Stress, Support 간격 Rule 개발 AI팀 + Piping Eng.
T2.3 I&C Module — 태그 일관성, SIL/SIF 로직, Control narrative vs P&ID Rule 개발 AI팀 + I&C Eng.
T2.4 General Checklist (Section A~F) 자동화 — 문서 완결성, Revision 무결성 체크 AI팀
T2.5 1차 내부 리뷰 — 샘플 도면 적용 + PE 검토 피드백 수집 PM + PKU 리뷰어
Phase 3 · Extended Disciplines — Mechanical / Electrical / Civil / Structural / Architectural
Week 11~16
KPI: 전체 8 Discipline Rule coverage ≥50% | Cross-discipline correlation 10개 항목 중 ≥7개 자동화
T3.1 Mechanical Equipment Module — Nozzle loads, 유지보수 clearance, 앵커볼트 AI팀 + Mech. Eng.
T3.2 Electrical Module — Load 계산, 케이블 크기, Hazardous Area 등급 AI팀 + Elec. Eng.
T3.3 Civil + Structural + Architectural 통합 모듈 (기초 설계, 하중, 건축 코드) AI팀 + Civil/Arch. Eng.
T3.4 Cross-Discipline Correlation Engine — P&ID vs 레이아웃, 태그 일관성 등 10개 항목 AI팀 (핵심)
T3.5 2차 중간 리뷰 — PKU와 공동 리뷰 세션, 우선순위 재조정 PM + 김상윤
Phase 4 · POC Delivery & Methodology Packaging
Week 17~20
KPI: End-to-end 리뷰 완료 1건 이상 | 리뷰 시간 절감 ≥30% vs 수동 | 클라이언트 만족도 ≥4/5 | Playbook v1 완성
T4.1 End-to-end 리뷰 워크플로 통합 — Rule Engine + Parser + Dashboard 연결 개발팀
T4.2 PKU 실제 IFC 도면 파일럿 테스트 (최소 1개 프로젝트 패키지) PM + PKU
T4.3 KPI 측정 및 최종 보고서 작성 (절감 시간, 정확도, 이슈 분류) PM + 김상윤
T4.4 SnapScale Project Playbook v1 — 이 방법론의 표준 문서화 전략팀
T4.5 프로젝트 갤러리 PKU 페이지 발행 (내부 공유용) PM

Section 7 · Repeatable Algorithm
반복 가능한 실행 알고리즘

PKU에서 검증 후, 다음 클라이언트에도 동일하게 적용할 수 있는 표준화된 절차 흐름입니다.

Client Checklist → AI Engine 표준 파이프라인
1
INTAKE — 체크리스트 수령 & 범위 확인
클라이언트로부터 문서 수령 → 분야·항목 수 카운트 → 계약 범위(Priority Disciplines) 확인 → 샘플 도면 데이터셋 요청
2
MECE PARSE — 구조화 & 온톨로지 매핑
자연어 항목 → 구조화 DB → CELab 온톨로지(EPC Stage × Domain × Type) 매핑 → Gap 리포트 생성 → 클라이언트 확인
3
PRIORITIZE — 고가치 Rule 20% 선정 (Pareto)
EPC 리스크 매트릭스 기반 우선순위 — LD·안전·IFC 릴리즈 블로커에 집중 → Rule 개발 순서 확정 → 도메인 전문가 검토
4
RULE BUILD — AI 검토 로직 개발 (분야별 Sprint)
2주 Sprint × N회 — 각 Sprint = 1개 Discipline → Rule 작성 → 샘플 도면 테스트 → PE 검토 피드백 → 수정
5
PILOT — 실제 IFC 패키지 적용 & KPI 측정
클라이언트 실제 IFC 도면 입력 → AI 리뷰 실행 → 결과 보고서 생성 → PE 검토 vs AI 결과 비교 → KPI 측정
6
PACKAGE — Playbook 업데이트 & 다음 클라이언트 준비
학습 내용 → Playbook 업데이트 → Rule 라이브러리 저장 → 프로젝트 갤러리 발행 → 다음 클라이언트 INTAKE 준비
3-1-1 요약 (김상윤 대표용):
결론: PKU 체크리스트는 ~370개 항목의 AI IFC QA/QC 엔진 개발 명세서이며, 이를 5개 JTBD + 4개 Phase 20주 실행 계획으로 변환했습니다.
근거 3: (1) 8 Discipline MECE 분석 완료, CELab 온톨로지 Gap 3개 식별. (2) 핵심 KPI 설정 — Coverage ≥60%, Accuracy ≥70%, Time Savings ≥30%. (3) 반복 가능한 6단계 알고리즘 확립 → 다음 클라이언트 적용 속도 2배.
